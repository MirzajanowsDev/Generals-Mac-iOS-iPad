# 2026-09 Development Diary

## 2026-09-08 — Issue triage day: #8 closed, Scudo hunt continues, Quest 3 + data import fixes

Follow-up to the August triage. Closed the confirmed-fixed issue, then went
after the remaining open ones. Built and booted everything on the OnePlus Pad
(OPD2415) over USB.

### Issue #8 closed — garrison-death crash confirmed fixed
`W3DTreeBuffer::unitMoved()` null-deref (fault 0x20) was fixed by `ed857fae`
in the v0.3 build; closed the issue with a full root-cause write-up and spun
the still-open magenta-tint half off into its own issue (#13).

### Quest 3 launch crash (#11) — window-size guard
The Quest's volumetric panel delivers a 1x1 `ANativeWindow` until the
compositor lays it out; creating the Vulkan surface in that state null-derefs
in the vendor driver (`vkCreateAndroidSurfaceKHR`, fault 0x98). The existing
ANativeWindow wait in `SDL3Main.cpp` only checked the pointer — it now also
polls `ANativeWindow_getWidth/getHeight` and waits for a non-degenerate
buffer (>1x1, same 5 s timeout) before letting `DX8Wrapper::Create_Device()`
run.

### Game-data import for Android 13+ (#12)
Android 13+ blocks file managers from writing into `Android/data/`, so the
"copy your .big files there" setup flow is broken on modern devices. New
`MainActivity` is now the launcher: if no GameData is visible (external
`Android/data/<pkg>/files/GameData` or internal `files/GameData`), it offers
a one-time SAF folder import (`ACTION_OPEN_DOCUMENT_TREE`) that copies the
picked install into internal storage, which the engine already supports as a
CWD fallback. No storage permissions needed. "Launch anyway" is still offered
for adb users.

### Scudo crash family (#4/#9/#6/#7/#10) — ROOT CAUSE FOUND AND FIXED
The decisive evidence chain:

1. A pool-disabled test build (`RTS_GAMEMEMORY_ENABLE=OFF`) crashed on the
   OnePlus in `DxvkResourceAllocationPool::alloc()` fault `0x2000000001` ~14 s
   in — same signature July notes had blamed on "Vulkan driver".
2. Re-enabling the pool did NOT fix it — and then the **stock v0.3 release
   APK crashed identically** on the same device: the device had updated
   Android 15 → 16. Same binary, new OS, new failure → allocator-state/timing
   dependent, not a code regression.
3. Reproduced on an **API-36 arm64 emulator** (Apple-Silicon host, game data
   staged into internal storage as root with `restorecon`): 100%
   deterministic `Scudo ERROR: invalid chunk state` abort at `SDL_main+564`
   — the exact signature of issues #4/#9 on real devices.
4. Symbolized `SDL_main+564` against the unstripped build: the crash is
   **`SDL_free()` on the pointer returned by
   `SDL_GetAndroidExternalStoragePath()`**.

**Root cause:** SDL3's Android storage-path getters
(`SDL_GetAndroidExternal/InternalStoragePath`, `SDL_GetAndroidCachePath`)
return **SDL-owned cached statics** (`static char *s_AndroidExternalFilesPath`
etc., `SDL_strdup`'d once). `SDL3Main.cpp` called them twice and
`SDL_free()`'d every result — five frees of SDL-owned memory, two of them
outright double-frees, plus use-after-free reads of the dangling statics in
between. What happens depends on the allocator-state lottery:

- 2nd free hits a **quarantined** chunk → immediate
  `Scudo ERROR: invalid chunk state` in `SDL_main` (issues #4/#9, emulator).
- 2nd free hits a chunk that was **already recycled and is live again** →
  no abort; instead a live allocation elsewhere gets freed under its owner →
  silent heap corruption surfacing later as the DXVK
  `DxvkResourceAllocationPool::alloc()` `0x2000000001` free-list garbage
  (menu crash on the OnePlus, likely also the #8-adjacent magenta tint #13 —
  freed texture memory getting reused).

**Fix:** remove all five `SDL_free` calls — the pointers belong to SDL and
are valid for the process lifetime.

**Verification:**
- API-36 emulator: the deterministic launch abort is gone; engine fully
  initializes (exits later at DX8 CreateDevice only because the emulator's
  gfxstream Vulkan lacks features DXVK needs — environmental, not our bug).
- OnePlus Pad (Android 16): game boots to menu and **runs** (3+ min, zero
  fatal signals; previously died in ≤100 s on every build, stock v0.3
  included).

**Addendum (post-release note):** a later repackage of the same code crashed
on the OnePlus within 75 s with the `0x2000000001` signature — the launch
abort fix stands (deterministic, emulator-proven), but a **second,
intermittent corruption source remains**: DXVK's
`DxvkResourceAllocationPool` free-list gets overwritten non-deterministically
after minutes of play. Control tests show stock v0.3 crashes the same way,
so v0.4 ships strictly better (launch crashes fixed, intermittent in-game
crash unchanged). An lldb hardware-watchpoint hunt on the pool's `m_next`
(conditioned on the exact corruption value) was set up but not completed —
see the watchpoint script approach in this session's notes; the NDK's lldb
needs libpython workarounds on macOS (Team-ID mismatch with brew python; use
Xcode's /usr/bin/lldb), and the on-device attach flow needs the app built
debuggable with lldb-server copied into the app's own data dir (run-as
cannot exec from /data/local/tmp). Also noted: a wedged game process
survived `am force-stop` in `t<` state (driver ioctl?) — possibly related,
possibly a separate Android 16 driver issue.

#### The earlier "engine heap overflow" theory — corrected
The working hypothesis mid-investigation (engine overflow masked by the pool)
was wrong: the pool-off build crashed for the same reason the pool-on build
did — the storage-path double-free. Android 16's allocator/timing shifted the
failure mode on this device; the corruption was there all along, on every OS.

#### ASAN groundwork (kept for future use)
Getting an ASAN build compiling required: scoping `-fsanitize=address` to
engine targets via `core_config` (global instrumentation breaks SDL3's hidapi
against NDK `jni.h`), disabling PCHs (`-DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`;
clang 18's PCH machinery mis-serializes `va_list` for ASAN TUs), and fixing
three latent include bugs the PCHs had been masking:
- `WWLib/STLUtils.h` + `Common/Errors.h` use `CPP_11` without including
  `CppMacros.h`; `Lib/BaseTypeCore.h` now provides it to every TU.
- `profile/internal.h` same story.
- `GameClient/Smudge.h` uses `std::hash_map` without
  `<Utility/hash_map_adapter.h>`.

The NDK r27 ASAN runtime itself SIGILLs at init on the OnePlus Pad (before
any game code), so on-device ASAN needs NDK r28 or different hardware — but
the emulator repro made ASAN unnecessary this time.
